# Rules of engagement

Written down so that neither a person nor an agent improvises in a public thread.

## Where we answer

Only where the pain is already public: an issue, a discussion, a request someone wrote
themselves. Their question is the invitation; nothing else is.

## What a first reply contains

1. The direct answer to what they asked — including "nobody can promise you that".
2. The specific item that could be blocking them, with the command that shows it.
3. Nothing else. No calendar link, no "book a demo", no price list pasted into a thread.

Offer #1 in [offers.md](offers.md) is free precisely so the first reply can be useful and
complete without a commercial ask.

## What we never do

- Post the same text in several threads. Two identical posts read as a bot.
- Bump a request for visibility. If the gate is manual, a bump is noise.
- DM someone who did not ask first.
- Quote a number without its date and source.
- Promise a `github.com/mcp` listing, a ranking, or a citation.
- Claim a review or audit that did not run — no "looks good" without a checklist.

## Disclosure

When a message is written with an agent's help, say so in one line. Several vendors in that
thread did, and it reads as honest rather than as a trick.

## Follow-up

One follow-up after a deliverable, when there is something new to say (a fix landed, a check
now passes). Not a "just checking in". If a person goes quiet, that is an answer.

## Language

English in public developer threads. Russian where the person wrote in Russian. Never machine
translate a message into a language neither side has used in the conversation.

## Record

Each public answer we publish is kept, dated, with the thread URL, in the private research
notes. If a number in it turns out to be wrong, the correction is published in the same place
rather than quietly edited away.
