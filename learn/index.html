02 🧱 The entry that survives a curator

You cannot speed up the queue. You can remove every reason to skip you when your turn comes. These are the items that appeared as actual blockers in requests published between 2026-10-28 and 2026-10-29.

  • ✓
    server.json validates against the current schemaAnd its name matches a namespace you actually own: a GitHub org, or a DNS-verified domain.
  • ✓
    A repository field, or a manifest that replaces itTwo maintainers wrote in their own request that the field was missing. A curator with no source has nothing to check.
  • ✓
    isLatest: true and a version that matches the packageA superseded version at the latest pointer reads as an abandoned project.
  • ✓
    Annotations on every tooltitle, readOnlyHint, destructiveHint, openWorldHint. Without them a client cannot prompt safely before a write.
  • ✓
    An auth shape a reviewer recognisesRemote servers: OAuth 2.1 + PKCE, protected-resource metadata, dynamic client registration. A bearer key pasted into config is not reviewable.
  • ✓
    Public endpoint evidenceAn unauthenticated curl that returns 401 with WWW-Authenticate beats any screenshot.
  • ✓
    One sentence that says what it does for a person"Manage your tasks" is a category. "Cancel a running job before the next billing interval" is a reason.
  • ✓
    A visible "what it does not do" lineIt is the cheapest trust signal you have, and the one reviewers check first.
⚠️

Do not re-post your request. In that thread, one maintainer bumped repeatedly for eight months. The listing arrived after a curator picked it up — not after a bump. Repeated asks add noise to a queue that is read by humans, and noise is the opposite of signal.

03 🧰 Tools an agent can actually choose

A tool description is not documentation for humans. It is the entire decision surface for a model that must pick one of your tools, or none. Write it for the model, and it stays readable for people as a side effect.

🎯

One job per tool

If the name needs "and", it is two tools. An agent that must guess which half will guess wrong on the expensive half.

🏷️

Verb-first, domain-specific names

tvijo_review beats process. The name is the first token a model sees and often the only one it ranks on.

🔒

Strict schemas

Reject unknown fields rather than ignore them. A silently ignored field is a wrong action the user never sees.

📦

Bounded output

Cap bytes, rows and age. An unbounded result is a context bomb, and it will be your server that gets blamed for the truncated answer.

🙈

Unknown is not zero

If you don't know the amount spent, return null and say so. Returning 0 turns an unknown bill into a false receipt.

🧯

Errors are content

Every failure gets a stable code and a sentence that tells the agent what to do next. "Something went wrong" forces a retry loop you cannot see.

04 💸 Money in an agent loop

The moment a tool can spend, the interface changes. An agent with a spend tool and no cap is a bug report waiting for a bill attachment.

  • Require the cap per call. No ambient default that spends without a number supplied by the caller. If the number is missing, refuse.
  • Clamp, don't negotiate. A session-level cap plus a hard ceiling per call. Above the ceiling: reject before the network request, so a bug costs nothing.
  • Never auto-retry a paid call. Ambiguity is resolved by a read-only lookup of the idempotency key, not by trying again and hoping.
  • Report the price next to the answer. A review that does not say what it cost is a review you cannot budget.
  • Say "unknown" out loud. A recovered result may carry spent_usd: null. That is honest; it is not zero.

05 🎨 Docs UX, applied to developer tools

Developer documentation is an interface. These five rules caught more real problems for us than any redesign.

🪜

1 · Progressive disclosure

The first screen answers "can I use this in five minutes". Schemas, edge cases and failure codes live one level down, linked, not inline. A page that starts with architecture loses everyone who was still deciding.

📋

2 · Copy-paste first

A working config block before the explanation of the config block. If a reader has to assemble a config from three sections, three of them will be wrong.

❓

3 · The three-question test

Can a stranger answer: what does it do, what does it cost, what breaks? If one answer is missing, the page is not finished — no matter how pretty it is.

🔎

4 · Visible state

Show the current state instead of describing it: version, sign-in state, remaining limit. A user who can see the state stops guessing and stops writing to support.

🧭

5 · One path, named exits

One recommended route through the page. Alternate clients and manual setups are exits from that route, not parallel tunnels at the top.

🧾

Bonus · Receipts over adjectives

"Fast" is an adjective. "0.2.0 published, registry active, gallery count: 0, observed 2026-10-29" is a receipt. Receipts survive reviews.

06 📣 Being quoted, not ranked

Search ranks pages. An assistant quotes sentences. The unit of work is a claim with a source and a date — not a keyword with a density.

  • 1
    Answer in the first paragraphThe first self-contained answer is what gets lifted. Preamble is dead weight.
  • 2
    One number, one definition, one dateSame quantity on two pages must mean the same thing, with a link between them. Two labels, no path, is a defect — even when both numbers are true.
  • 3
    Make the method visibleThe command, the endpoint, the version. A claim nobody can reproduce is a claim nobody should quote.
  • 4
    Always add "when this does not work"The boundary is the most useful sentence on the page, and the one competitors omit.
  • 5
    Structure an extractor can liftOne H1, question-shaped H2s, tables for comparisons, FAQ whose questions are the real questions, JSON-LD, llms.txt.
  • 6
    Publish the negative resultAn autopsy of a culled experiment gets cited more than another success story, because almost nobody writes one.
🪞

Rule of the second pass. If a verdict matches the wording of the question too neatly, check it again with a different instrument. Three models agreeing on the same wrong reading agree confidently.

07 📈 The only loop worth running

  • Entry is correct. Schema, repository, annotations, honest description. Nothing else matters until this is true.
  • Install is five minutes. One command, one config block, one visible state. Measure how long it actually takes a stranger.
  • The first call returns a receipt. Cost, task id, state. The receipt is the product, not a detail.
  • A public page answers the question they will type. Dated, sourced, with its own limits written down.
  • Someone repeats it in public. Not a testimonial you wrote; a sentence they wrote because the cap did what it said.

08 ⚠️ When this does NOT work

🚫

When you need the gallery tomorrow

You can't. It is a manual gate with no published ETA. If a launch depends on it, the launch is already unscheduled. Ship the manual install path as the real path.

🧲

When the product is the listing

If being visible is the whole value, the server has no independent job. A curator notices that, and so does the first user who installs it.

🕳️

When you cannot show a receipt

No version, no endpoint, no dated check — then no claim. "It works" is not evidence, and a page built from it will not be quoted.

🔁

When the loop is actually a bug report

If users bounce at install, no amount of AEO fixes it. Fix install first; the page only amplifies what is already there.
